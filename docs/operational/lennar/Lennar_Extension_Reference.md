# Lennar Extension Reference

What sessions need to know about the Chrome extension used to fill CVRMLS Matrix fields for Lennar listings. Oriented toward the session's role in coordinating with Andrew — not toward extension internals or maintenance. Session-relevant only.

---

## 1. What It Is

A Chrome extension that reads a JSON payload from a persistent side panel and populates Matrix fields on the currently-active Matrix tab. It replaces the earlier per-tab bookmarklet system, which required Andrew to click a different bookmarklet on every Matrix tab and re-paste the payload every time Matrix reloaded the page (which happens on every tab click).

The extension's architecture is builder-agnostic. It acts as a Lennar-specific tool because it consumes Lennar-shaped payloads generated by sessions in this project — not because it internally hardcodes Lennar. Sessions can rely on this behavior without needing to reason about it further.

---

## 2. How It Works — Session-Relevant View

**One paste, persistent panel.** Andrew opens the Chrome side panel, pastes the payload once, and moves through Matrix normally. Matrix does a full page reload on every tab click, but the side panel persists across those reloads. The payload does not need to be re-pasted per tab.

**Tab detection.** The extension recognizes which Matrix tab is currently visible by inspecting known field IDs on the page. Detection covers the 11 Lennar-scoped tabs (see §5). Unknown or non-Lennar tabs are ignored.

**Fill mode — auto or manual.** A toggle in the side panel controls whether fills happen automatically the moment a known tab is detected, or wait for Andrew to click "Fill current tab" as a manual checkpoint. Default is off (manual). Andrew's preference persists across sessions.

**Per-tab status list.** The side panel shows all 11 Lennar-scoped tabs with a color-coded status per tab: unvisited, pending, filled, or error. Status is in-memory only — closing and reopening the side panel resets the visible list, though the underlying payload and toggle preference persist.

**Field-write logging.** Every field write is logged internally with the field's outcome. If a field the payload targets is not found on the page, or fails to write, it surfaces in the log as an error rather than silently succeeding. This is how the operational project catches drift between the schema and Matrix's actual DOM.

---

## 3. What Andrew Does

- Copies the generated payload from the session's output to the clipboard.
- Opens the Chrome side panel in Matrix, pastes the payload once.
- Clicks through the Lennar-scoped Matrix tabs manually. Full auto-navigation between tabs is not implemented — Andrew controls tab movement.
- Watches per-tab status update as the extension fills each tab.
- Reports back to the session with the outcome — either "all clean" or specifics on any errors, missing fields, or unexpected behavior.
- Handles the always-manual Matrix fields separately (see §5).

---

## 4. What the Session Does With Andrew's Feedback

**Clean fills across all tabs.** Session confirms and proceeds to the next protocol step (Airtable update, Google Sheet entry, addendum sending, etc. per the New Listing Protocol).

**Field-write errors reported.** Session acknowledges the specific field(s), works around the issue with Andrew if the listing needs to be published anyway (typically by having Andrew enter the field manually in Matrix), and generates an Issue Report artifact per §4.2 of the Project Protocol. The Issue Report is the escalation channel — the operational session does not attempt to diagnose or fix the field-write issue itself.

**Detection miss on a known tab.** Same treatment — the session flags it, coordinates a workaround if needed, and produces an Issue Report. A detection miss often means either the tab's detection signature has drifted or the extension is out of sync with the current schema.

**Extension not behaving as documented here.** If Andrew reports the extension doing something this doc doesn't describe, treat it as an Issue Report candidate. The extension's behavior and this reference should stay in sync; drift between them is worth surfacing.

---

## 5. What the Extension Does and Does Not Cover

**The 11 Lennar-scoped Matrix tabs the extension handles:**

Listing Info, Bath Info, Features (single physical tab with A and B fill functions), General Info, Remarks, Fee Info, Owner Info, Agent/Office Info, Showing Instructions, Virtual Tour Info, Internet Display Info.

**Not covered by the extension:**

- **Room Info tab.** Lennar listings skip this tab entirely per builder convention.
- **Full auto-navigation between tabs.** Deferred post-MVP. Andrew clicks tabs manually.
- **Cross-MLS or cross-builder routing.** The extension processes whatever payload it receives. Sessions in this project only generate Lennar/CVRMLS payloads.

**Matrix fields that are always manual, regardless of the extension:**

Some Matrix fields must be entered by Andrew directly and are never touched by the payload or the extension:

- **Map** (map pin placement)
- **Directions** (driving directions text)
- **Subdivision** (dropdown selection that requires Matrix's live subdivision lookup)
- **Post Office** (dropdown selection)

Sessions should flag these in the intake handoff so Andrew enters them when he's in Matrix reviewing the extension's fills. They are not extension defects when unfilled — they were never in scope for any fill mechanism.
